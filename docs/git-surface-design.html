Design and architecture only. The companion interactive concept uses sample history. Production code and repository settings have not been changed.

The experience

The surface should answer four questions immediately: Where am I working? What work exists elsewhere? Which plan produced these changes? What will happen if I save, combine, or share them?

Use a stable, two-dimensional history map with organic paths. Commits are nodes; branches are named pointers to nodes; merges join real parent histories. Keep the same positions while a user explores. Animation expresses a change in state without continuously rearranging the map.

The left list provides every local and remote branch through search and paging; the canvas renders a bounded view. A new branch appears immediately at its starting commit, even before it has unique commits. Group merged or inactive branches rather than deleting their history. Offer the equivalent list view for dense repositories and accessibility.

Cards open the exact plan revision and code-review diff. A branch card summarizes all explicitly connected plans, their review state, unique commits, and linked working folders. Measured impact means changed files, actual diffs, test results tied to a commit, and publication records. Do not equate a passed check with proof that a plan was fully fulfilled.

Use plain labels alongside Git terms: “Save checkpoint · commit,” “Combine changes · merge,” and “Share branch · push.” Keep Git terminology discoverable so the interface teaches transferable knowledge.

State must tell the truth

A branch needs several independent status dimensions. A branch can be clean in one working folder, contain unpublished commits, await review, and be checked out by a running agent at the same time.

Repository facts

  • Local and remote refs, upstream relationship, default branch, commit parents, tags, detached or unborn HEAD.
  • Exact ahead/behind counts relative to the named upstream, with last-fetch time. Unknown remote state stays unknown.
  • Working-folder identity, staged/unstaged/untracked changes, conflicts, and an operation already in progress.
  • Other worktrees and active Redline runs using them. An unobserved worktree is not assumed clean.

Redline facts

  • Plan revision and content hash; approval decision; run and review identity.
  • Explicit implementation links to individual commits, plus broader run-boundary observations.
  • Validation results with the exact commit or working snapshot they measured.
  • Agent proposal, user decision, effective policy version, and operation outcome.

Unsaved changes belong to a worktree, not to every branch. Git worktrees share repository data but have their own HEAD and index. The UI can present these as “working folders.” Git worktree documentation.

Use many-to-many links: one plan can span branches and commits, and one commit can implement several plans. Store the exact revision and preserve its content hash; later plan edits cannot silently relabel earlier work. An observation such as “run started on this branch” is not an implementation claim. A base-to-tip range is context unless individual commits were attributed or the user confirms the range.

Capture links at plan approval, run start, review creation, commit creation, and publication. These events have distinct relation types. A branch rename preserves historical names; deletion preserves a tombstone. Rebase or squash creates new commit identities: record an explicit replacement mapping when known, otherwise mark the link unresolved. Preserve old evidence and let the user correct associations through additional events.

Import existing run, queued-review, and push records only where the relationship is evidenced. Existing plans with just a project path show “No recorded commit link.” Never infer authorship from proximity in time or similar branch names. Commit IDs are opaque values; do not assume a fixed SHA length.

Architecture inside Redline

Add one lazy-loaded Git surface with a graph, branch list, contextual inspector, action previews, and guide inbox. React Flow is already installed; use it for the viewport and accessible custom nodes, with deterministic graph layout calculated in a worker. Cards and hit targets remain DOM elements. Render only the visible history and cache layout by commit identity.

Refresh, scale, and consistency

Watch resolved Git metadata—including HEAD, refs, packed refs, index, and linked-worktree metadata—and relevant working-folder changes. Debounce bursts, invalidate affected caches, and reconcile on focus and periodically to recover missed events. The current folder-explorer watcher is not sufficient on its own because it intentionally avoids watching all of Git metadata.

Snapshots carry a generation and completeness flags. Verify refs and working-state markers before and after a scan; retry or mark the snapshot stale if they change. A failed read must not become “clean,” “zero ahead,” or “no conflict.” Remote state is explicitly as-of the last successful fetch; network refresh is a separate, configurable action.

Load branch inventory independently of commit pages so an old branch never disappears because its tip is outside the visible history window. Collapse linear sequences without losing merge boundaries, selected nodes, plan links, or branch tips. Preserve camera and selection during refresh. Proposed acceptance targets: interactive hover stays local to cached data; no Git call per pointer event; validate responsiveness with 500 refs and 100,000 commits while only a bounded window is rendered.

Grounding in the current repository

  • review.rs already enumerates branches and renders several diff sources; its existing picker caps each branch category at 200. The new inventory must expose paging/completeness instead of silently inheriting that cap.
  • push.rs already provides status and guarded commit/push actions. Its write entry points are Tauri commands, while the agent-facing Git bridge is read-only. Preserve that boundary. The existing status probes tolerate errors; the new snapshot model must distinguish probe failures from empty state.
  • ReviewSession records the project and plan revisions; CodeReviewSession records a repository and optional commit; PushRecord records a publication destination. These are useful inputs, but not a complete plan-to-commit model.
  • runner_graph.rs links runs to plan sessions. queue.rs preserves parked review-to-plan relationships. ledger.rs and the Polis store retain attributed, append-only decisions.
  • shipwright.rs demonstrates evidence-backed structured findings. It does not currently implement the proposed isolated-worktree executor; that remains new work.
  • work.rs deliberately excludes branch/worktree execution ownership from work items. Keep Git execution state in the new Git service, linked by provenance, rather than breaking that boundary.

Every write is a previewed operation

prepare(action, repository, worktree, expectedSnapshot)
  → source and destination, exact affected paths/refs,
    measured conflicts, policy results, expected effect, recovery option

apply(preparedOperationId, userDecisionId)
  → revalidate → execute typed steps → reconcile actual state → record outcome

The preview is bound to a digest of relevant source/target commit IDs, selected contents, index state, working-tree state, and effective policy. Approval authorizes that exact operation. If another agent or terminal changes its inputs, invalidate it and generate a new preview. Do not convert a model response into an arbitrary shell command.

Use a repository-wide Redline operation queue plus Git’s own locking and expected-old-value checks where applicable. These serialize Redline operations, not external Git clients; external activity still requires validation and post-operation reconciliation. Checked-out worktree changes must use Git’s working-tree-aware operations. Do not move a checked-out ref with a bare ref update and leave its files behind. Git reference transactions.

PushShow the exact remote and destination ref; recheck remote state and protection. Publish only the chosen commits. A push must not silently merge, rebase, force-update, or delete a remote branch.

A conflict preview measures mergeability, not correctness. Validation runs and their results remain separate. Merge previews can use Git’s actual merge implementation without modifying the user’s current index or files. Git merge-tree documentation.

Persist the operation intent before execution and record completed steps as they happen. A commit followed by a failed push is “Saved locally; sharing failed,” with the commit retained. After a crash or network timeout, reconcile local refs and the remote before offering retry; an unknown outcome must not trigger a blind duplicate write. Recovery checkpoints have explicit retention and cleanup rules.

The asynchronous Git guide

Begin with a read-only observer and proposal author. It receives a versioned snapshot and provenance digest, runs inexpensive deterministic checks, and invokes a configured model only when explanation or judgment adds value. File-save bursts should not launch repeated model calls.

Teach

Explain the actual selected branch: “These two checkpoints are saved on this computer but haven’t been shared.” Offer a short explanation of the next action and an expandable technical view. Let users choose guidance density and silence lessons they already understand.

Optimize

Identify concrete issues such as missing plan links, abandoned unshared work, repeated conflict hotspots, or a rule that causes frequent overrides. Cite exact commits, paths, decisions, and measurements. Suggestions based only on a branch name or model intuition remain suggestions, not facts.

Configure

Propose precise diffs to project rules and supporting skills, with scope, rationale, examples, and validation. Show which commands or workflows enforce each rule and where it is only advice.

Remain accountable

Users can approve, edit, dismiss, defer, pause the guide, or restore an earlier rule. Record the evidence and decision. Dismissal prevents repeated rewordings of the same proposal unless the underlying evidence changes.

Persist jobs with pending/running/completed/stale/failed states, input digests, cancellation, deduplication, bounded concurrency, and retry limits. Pause or mark results stale when relevant state changes. Notify only when a useful proposal, failure, or required decision appears. The user can configure frequency, provider, cost limits, and notification behavior through existing agent settings.

Version control for rules and skills

Proposed defaults: tracked project policy in .redline/git-policy.json, and a matching repository skill under skills/git-hygiene/SKILL.md. Review both as one patch and land them together as an ordinary commit. The approval records the policy base hash, patch hash, model identity, evidence, test results, and resulting commit. Version 4 can restore the contents of version 2 while retaining version 3 and the intervening decisions.

Local Git configuration is separate because .git/config is not part of ordinary tracked history. Use allowlisted, project-scoped configuration changes with before/after values and a recovery record. Do not serialize credentials into the policy or ledger. Global configuration needs its own explicitly scoped proposal. A policy that should apply across all local worktrees must not silently vary with whichever branch happens to be inspected; record the approved effective policy commit.

Rules have an enforcement level: advisory, enforced by Redline operations, or independently enforced by repository hooks/CI/hosting. Redline cannot claim to prevent terminal writes or enforce remote branch protection merely by displaying a rule. Installation or modification of executable hooks is an explicit reviewed capability change.

The guide can propose a rule change, but cannot grant itself new execution privileges, bypass an approval, or amend its own authority. All approved Git mutations pass through the same typed action engine used by the human-facing controls.

Fixtures that matter

Use temporary real repositories with a bare remote: shared ancestors; branch creation without a commit; fast-forward, normal merge, squash, and cherry-pick histories; branches deleted or renamed; force-updated remote refs; filenames with tabs/newlines; Unicode ref names; partial staging; two worktrees; an external writer racing approval; a failed push after a successful commit; and restart midway through an operation. Treat Git history and provenance as separate truths in every fixture.

For the UI, verify hover paths, pinned cards, focus retention, touch access, reduced motion, list equivalence, narrow layouts, and no canvas relayout while inspecting a card. Include a novice usability test: can someone identify where work is saved, where it is shared, which plan produced it, and what their next click changes?

Decisions to carry into implementation

  • Organic, stable 2D paths; no force-directed simulation as the default.
  • A first-class Git destination, with contextual entry from plans, runs, and Code Review.
  • Plain-language actions with Git terms alongside them; exploration and checkout are separate.
  • Explicit, revision-specific provenance; incomplete historical attribution remains visible.
  • Project-scoped guide proposals and tracked rules; human approval bound to exact state.
  • Initial action scope excludes automated rebase, force-push, and bulk branch deletion. Add advanced operations only with their own preview and recovery contracts.
